# 阶段4：游戏关卡生成器与可玩原型 - 详细可执行方案

## 一、目标与范围

### 目标
在阶段3（游戏设计参考工具）的基础上，进一步实现**从案例到游戏关卡的自动化生成**，并制作一个**可交互的推理游戏原型**，验证游戏模板的实际可用性，使网站从"设计参考"升级为"设计+原型验证"工具。

### 核心价值
- **游戏设计师**：输入一个案例，一键生成基于模板的完整关卡结构文档，可直接用于开发
- **创作者**：通过可玩原型体验不同模板的玩法，获取设计灵感
- **验证价值**：用实际可玩的游戏验证5个游戏模板的设计合理性

### 范围
- **功能1：游戏关卡生成器**（P0）
  - 输入：选择案例 + 选择游戏模板
  - 输出：完整的关卡结构文档（阶段设计、线索分配、机制配置、难度曲线）
  - 支持导出为Markdown/JSON

- **功能2：可玩原型 - 推理审判模板**（P0）
  - 基于"推理审判模板"制作一个可交互的文字推理游戏
  - 使用1-2个案例作为游戏内容（如东方快车谋杀案）
  - 核心玩法：证据收集 → 法庭辩论 → 真相揭露
  - 纯前端实现，无需后端

- **功能3：原型入口与展示页**（P1）
  - 在游戏设计总览页添加"可玩原型"入口
  - 原型展示页：介绍原型玩法、技术实现、设计思路

### 不在范围
- 不做完整的游戏引擎或复杂的图形渲染
- 不做用户账号和云端存档（原型进度本地存储）
- 不做移动端适配优化（原型优先桌面端体验）
- 不做音效和背景音乐（可后续添加）

### 2.2 生成逻辑

#### 输入处理
1. **案例选择**：从56个案例中选择，支持按名称搜索、按类型筛选
2. **模板选择**：从5个模板中选择1个
3. **智能推荐**：根据案例的诡计类型，自动推荐最适配的模板（高亮显示）

#### 生成算法
```
输入：案例C + 模板T
输出：关卡结构文档D

1. 基本信息
   D.案例名 = C.基本信息.案件名称
   D.模板名 = T.name
   D.核心诡计 = C.设计视图.核心诡计简述
   D.适配诡计 = T.适配诡计类型 ∩ C.设计视图.诡计类型

2. 阶段设计（遍历T的4个阶段）
   对每个阶段S：
   D.阶段[i].名称 = S.阶段
   D.阶段[i].玩家目标 = 结合C的故事内容改写S.玩家目标
   D.阶段[i].关键机制 = S.关键机制
   D.阶段[i].线索分配 = 从C.设计视图.线索链中筛选匹配该阶段的线索
     - 线索时机映射：开篇→阶段1，前期→阶段2，中期→阶段3，后期/终局→阶段4
   D.阶段[i].设计要点 = S.设计要点 + 针对C的特点补充

3. 难度曲线
   D.难度曲线 = T.难度曲线
   D.难度评分 = C.设计视图.难度评分

4. 机制配置表
   D.机制配置 = 列出T中所有机制，结合C的特点说明如何实现

5. 改编建议（如果C有游戏化改编建议）
   D.改编建议 = C.设计视图.游戏化改编建议中与T最匹配的方向
```

#### 线索分配映射规则
| 模板阶段 | 对应线索时机 | 说明 |
|----------|-------------|------|
| 阶段1（案件发生/引入） | 开篇 | 背景信息、初始线索 |
| 阶段2（证据收集/探索） | 前期 | 关键线索、可调查对象 |
| 阶段3（推理/辩论） | 中期 | 矛盾点、转折线索 |
| 阶段4（真相揭露） | 后期、终局 | 决定性证据、真相线索 |

### 2.3 导出功能
- **Markdown导出**：生成结构化的Markdown文档，可直接复制使用
- **JSON导出**：生成结构化JSON，可用于后续开发或导入其他工具
- 导出方式：前端生成文件，触发浏览器下载

### 2.4 技术实现
- 纯前端实现，所有逻辑在客户端完成
- 使用现有的 `caseLoader.ts` 加载案例和模板数据
- 生成逻辑封装为独立的工具函数 `src/lib/generator.ts`
- 输出区域使用可折叠面板，方便查看长文档

## 三、功能2：可玩原型 - 推理审判模板

### 3.1 原型概述

#### 游戏名称
《东方快车：推理审判》（暂定）

#### 核心玩法
基于"推理审判模板"，玩家扮演侦探波洛，在东方快车上调查谋杀案：
1. **调查阶段**：在列车车厢中探索，收集证据，询问乘客
2. **法庭阶段**：在餐车进行"审判"，通过出示证据指出证词矛盾
3. **真相阶段**：还原案件真相，做出最终选择

#### 案例选择
- **主案例**：东方快车谋杀案（有改编建议，诡计类型匹配推理审判模板）
- **备选案例**：逆转裁判1-2（游戏案例，可直接复用其游戏设计）

### 3.2 游戏结构

#### 场景设计
```
场景1：波洛的包厢（开场）
- 介绍背景：列车因雪被困，发现受害者
- 目标：了解案件概况

场景2：受害者包厢（调查）
- 可交互物品：尸体、窗户、桌子、烟灰缸、手帕、怀表
- 收集证据：5-6件关键证据

场景3：走廊（调查）
- 可进入的乘客包厢：12个（简化为5-6个关键乘客）
- 每个乘客可对话，获取证词

场景4：餐车（审判）
- 所有乘客聚集
- 玩家依次询问乘客，可出示证据指出矛盾
- 3-4个关键矛盾点需要揭露

场景5：结局（真相）
- 玩家选择：揭露真相 / 替乘客保密
- 两个结局
```

#### 核心机制

##### 机制1：证据收集
- 玩家点击场景中的物品收集证据
- 证据记录在"证据栏"中，可随时查看
- 每件证据有：名称、描述、关键信息

##### 机制2：证词与矛盾
- 乘客有初始证词
- 玩家可以"追问"获取更多信息
- 玩家可以"出示证据"指出证词矛盾
- 正确出示证据推进剧情，错误出示扣除"信心值"

##### 机制3：信心值系统
- 玩家初始信心值：100
- 错误出示证据：-10
- 正确指出矛盾：+20
- 信心值影响结局评价（S/A/B/C）

##### 机制4：多结局
- 结局A（真相）：揭露全员凶手，波洛选择报警
- 结局B（宽容）：揭露真相但替乘客保密，波洛选择隐瞒
- 结局评价基于信心值和关键选择

### 3.3 数据结构

#### 游戏状态
```typescript
interface GameState {
  currentScene: string;           // 当前场景
  collectedEvidence: string[];    // 已收集证据ID
  interviewedWitnesses: string[]; // 已询问证人ID
  contradictionsFound: string[];  // 已发现矛盾ID
  confidence: number;             // 信心值
  choices: Record<string, string>; // 玩家选择记录
  gamePhase: 'intro' | 'investigation' | 'trial' | 'ending';
}
```

#### 证据数据
```typescript
interface Evidence {
  id: string;
  name: string;
  description: string;
  keyInfo: string;          // 关键信息（用于矛盾点）
  scene: string;            // 所在场景
  foundIn: string;          // 具体位置
}
```

#### 证人数据
```typescript
interface Witness {
  id: string;
  name: string;
  description: string;
  initialTestimony: string;   // 初始证词
  followUpTestimony: string;  // 追问后证词
  contradiction: {
    evidenceId: string;       // 指出矛盾所需证据
    description: string;      // 矛盾描述
    revealed: boolean;
  } | null;
}
```

### 3.4 技术实现

#### 技术方案
- **框架**：纯Astro + 原生JS（不引入额外游戏引擎，保持轻量）
- **状态管理**：使用Reactivity Store（Astro Islands）或简单的全局状态对象
- **UI组件**：
  - `GameScene.astro`：场景渲染（背景+可交互物品）
  - `EvidenceBar.astro`：证据栏
  - `DialogBox.astro`：对话框
  - `TrialPanel.astro`：审判面板
- **存档**：localStorage存储游戏进度

#### 页面结构
```
/fun_detective/game-design/prototype/
├── index.astro          # 原型入口页（介绍+开始游戏）
├── play.astro           # 游戏主页面
└── components/
    ├── GameScene.astro      # 场景组件
    ├── EvidenceBar.astro    # 证据栏
    ├── DialogBox.astro      # 对话框
    └── TrialPanel.astro     # 审判面板
```

#### 游戏流程实现
1. **开场**：文字叙述 + 点击继续
2. **调查**：点击场景物品收集证据，点击证人对话
3. **审判**：选择证人→查看证词→追问/出示证据→揭露矛盾
4. **结局**：根据游戏状态显示对应结局

### 3.5 内容工作量

| 内容类型 | 数量 | 说明 |
|----------|------|------|
| 场景 | 5个 | 包厢、走廊、餐车等 |
| 证据 | 8-10件 | 从案例线索链中选取 |
| 证人 | 5-6个 | 12名乘客简化为关键角色 |
| 矛盾点 | 3-4个 | 核心推理环节 |
| 对话文本 | 约3000字 | 证词、追问、剧情 |
| 结局 | 2个 | 真相/宽容 |

## 十、风险与应对

| 风险 | 影响 | 应对方案 |
|------|------|----------|
| 原型内容工作量大 | 时间延长 | 优先完成核心流程（1个场景+3个证据+2个矛盾点），内容逐步扩充 |
| 游戏状态管理复杂 | 开发难度高 | 使用简单的全局状态对象，不引入复杂状态管理库 |
| 生成器结果质量不高 | 用户体验差 | 提供"重新生成"和"手动编辑"选项，生成结果作为参考而非最终 |
| 原型玩法单调 | 体验不佳 | 增加信心值系统和多结局，增加重玩价值 |
| 纯前端游戏性能问题 | 卡顿 | 控制DOM数量，使用CSS动画而非JS动画 |
| 案例改编版权问题 | 法律风险 | 明确标注"基于XX案例改编，仅供学习参考"，不用于商业用途 |
