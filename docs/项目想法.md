# Fun Detective 项目想法

## 一句话定位

Fun Detective 是一个把全球案件资料结构化，并进一步转化为推理游戏关卡的创作工作台：用户可以查案例、拆诡计、套用玩法模板、生成关卡方案，再用可玩原型验证设计。

## 对外简介

Fun Detective 面向推理小说作者、独立游戏设计师和喜欢研究案件结构的玩家，提供从“找灵感”到“做玩法”的一站式工具。项目收录推理小说、影视、游戏和真实案件，通过案件视图、诡计机制、线索链和游戏模板，把零散的故事资料变成可检索、可比较、可复用的设计资产。

## 我对项目的判断

这不是单纯的案件百科，也不是一个只展示故事的静态网站。它最有价值的方向是“案件知识库 + 关卡生成器 + 可玩验证”的组合：

1. 案例库提供内容和灵感来源。
2. 诡计与机制映射提供设计语言。
3. 游戏模板把设计语言组织成关卡结构。
4. 可玩原型检验结构是否真的好玩。

目前项目已经具备这条主链路的雏形：约 56 个案例、5 个游戏模板、10 类诡计映射，以及《东方快车：推理审判》可玩原型。技术上采用 Astro + TypeScript + Tailwind，数据由飞书 Base 同步到 JSON，再静态构建发布，适合低成本维护和公开展示。

## 目标用户

- 推理小说、剧本和短篇创作者：寻找诡计、人物关系和线索节奏参考。
- 独立游戏设计师：快速把案件改造成审判、密室、时间回溯等玩法结构。
- 推理爱好者：以更结构化的方式阅读和比较案件。
- 教学或工作坊组织者：用模板和原型讲解叙事、关卡与信息设计。

## 核心使用流程

```text
浏览案例 → 筛选诡计与地区 → 查看线索链/设计视图
       → 选择游戏模板 → 生成关卡结构 → 导出 Markdown/JSON
       → 在可玩原型中验证 → 反馈并迭代案例或模板
```

## 核心产品模块

### 1. 结构化案件库

每个案例同时提供基本信息、故事视图、设计视图和游戏设计视图。用户不只看到“发生了什么”，还可以看到诡计类型、信息差、红鲱鱼、线索时机和可复用机制。

### 2. 诡计到机制的映射

把“密室”“不在场证明”“身份诡计”等叙事诡计，映射到证据收集、矛盾指证、时间线重构、多视角切换等可实现机制，帮助创作者从故事问题走向玩法方案。

### 3. 关卡生成器

输入一个案例和一个模板，自动生成基本信息、四阶段流程、线索分配、机制配置和改编建议，并支持 Markdown/JSON 导出。生成结果应被定位为“高质量初稿”，保留人工编辑空间。

### 4. 可玩推理原型

当前原型以东方快车为案例，包含调查、证据收集、证人询问、矛盾指证、信心值和双结局。它的意义不是做成完整商业游戏，而是验证模板中的信息节奏和推理动作。

## 差异化价值

- 内容和玩法在同一份数据模型中，减少从“看故事”到“做游戏”的转换成本。
- 线索链带有出现时机，可直接映射到关卡阶段，而不是只做标签检索。
- 模板是可复用的设计资产，未来可以持续增加案例和原型。
- 生成器结果可以导出，便于进入策划、写作或开发流程。
- 原型验证让设计方案接受实际交互检验，而不止停留在文档层面。

## MVP 建议

当前 MVP 已经足够展示产品方向，下一阶段应优先提高“第一次使用的成功率”，而不是盲目扩充数据量：

1. 修复生成器点击后的无条件提示，错误信息改为页面内状态反馈。
2. 为生成结果加入手动编辑、重新生成和复制按钮。
3. 让原型的任务目标、调查进度和证据关系更明确，减少“点击试错”。
4. 优先完成第二个模板原型（建议密室逃脱），验证模板体系是否可迁移。
5. 将 `/fun_detective/` 这类部署前缀集中配置，避免页面脚本中的路径散落。

## 后续路线

### 阶段 5：创作效率

- 关卡结构在线编辑和版本保存。
- 线索拖拽编排、证据关系图和时间线视图。
- 生成结果的一键复制、导出和分享链接。

### 阶段 6：内容扩展

- 为密室逃脱、连环案件、多视角叙事、时间回溯分别制作最小可玩原型。
- 增加原创虚构案件，降低真实案件的版权和伦理风险。
- 建立案例质量字段：来源可信度、剧透等级、内容敏感度、适合改编范围。

### 阶段 7：社区与智能辅助

- 用户提交和分享自制案例、模板及关卡。
- 基于诡计、机制和难度的相似推荐。
- 引入 AI 作为“设计助手”，负责提出变体和检查逻辑，不直接替代作者判断。

## 数据与技术原则

- 飞书 Base 继续作为录入入口，Git 仓库保存可审查的数据资产。
- JSON Schema、同步校验和归档机制保持不变，新增字段先更新 schema 再更新页面。
- 前端优先保持静态化；只有用户作品、分享和协作功能出现后，再考虑后端服务。
- 真实案件内容明确标注资料来源、非官方立场和敏感内容提示。

## 风险与边界

- 真实案件涉及受害者和家属，展示应避免猎奇化、过度细节和未经证实的断言。
- 影视、小说和游戏案例只做学习与设计参考，不能暗示版权授权。
- 自动生成容易产生“结构完整但推理不成立”的结果，必须保留人工审核和编辑环节。
- 原型目前偏文字交互，视觉、音效和移动端适配应作为体验增强项，不应掩盖核心推理质量。

## 当前验收记录

- `npm run build`：构建完成；Vite 对部分 Astro 优化依赖有警告，需要后续清理。
- Python 测试：当前环境未安装 `pytest`，本次不能据此声明测试通过。
- 已发现的体验问题：关卡生成器脚本在真正生成前会无条件弹出提示，属于应优先修复的 P0 交互问题。

## 项目成功标准

项目成功不以案例数量为唯一指标，而以用户能否完成一次完整创作闭环衡量：

- 新用户能在 3 分钟内找到一个适合的案例和模板。
- 用户能生成一份可直接继续编辑的关卡初稿。
- 原型能让用户验证至少一个核心推理动作，而不是只浏览文本。
- 新增案例和模板不需要修改多处页面逻辑。

## 最终愿景

把 Fun Detective 做成“推理内容的设计基础设施”：既能沉淀案件知识，也能帮助创作者把诡计、线索和叙事结构转译成可玩的交互体验。
