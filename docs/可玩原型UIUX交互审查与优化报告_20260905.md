# 可玩原型 UI/UX 与交互审查报告

**审查日期**：2026-09-05  
**审查范围**：线上 `game-design/prototype/` 的东方快车：推理审判、血字的研究、逆转裁判：最初的逆转；对应的原型入口页、通用游戏壳和交互组件。  
**审查方式**：桌面端线上体验、可访问性树检查、关键流程与源码对照；以 `ui-ux-pro-max` 的无障碍、触控、响应式和反馈规范，以及 `frontend-design` 的沉浸式体验与信息层级原则为基准。

## 结论摘要

三个原型已经具备一个可继续扩展的共同引擎：案件选择、开场、调查或法庭、证据、笔记、时间线、关联板、审判和结局都已出现。这是正确的产品方向。

但当前体验更像功能集合，而不是一段聚焦的推理体验。最优先的问题不是增加更多系统，而是修复入口可读性、让三款游戏能可靠加载、把顶部工具条收敛为与当前任务相关的操作，并校正教程和案件流程的契约。否则玩家在第一分钟会遇到“看不清、看不懂、点不到或不知道为什么要点”的问题。

**总体评级：6/10（可演示原型，尚未达到稳定对外体验标准）**。

| 维度 | 评价 | 说明 |
|---|---:|---|
| 产品结构 | 7/10 | 三案件、共用引擎和多种推理工具已经形成基础。 |
| 首次体验 | 4/10 | 入口可读性、启动反馈和信息优先级明显影响进入游戏。 |
| 交互反馈 | 6/10 | 证据卡、Toast、确认弹窗有基础，但关键行为仍依赖文字说明。 |
| 推理参与感 | 6/10 | 证据、关联、时间线和笔记方向正确，但有较多“系统先告诉玩家答案”的倾向。 |
| 视觉一致性 | 5/10 | 主站浅色页面与原型深色界面切换突兀；结构图标混用 emoji。 |
| 无障碍与移动端 | 3/10 | 焦点、语义、触控尺寸和小屏工具条均未充分处理。 |
| 可扩展性 | 7/10 | 数据化流程已有雏形，但教程、目标和状态仍存在硬编码残留。 |

## 已验证体验

### 原型入口

- 三张案件卡均能展示名称、难度、预计时长、类型与标签。
- 在线上桌面截图中，页面 H1 使用 `text-white`，但入口页面背景是浅色，标题几乎不可见。
- 三张卡片由可点击 `div` 组成，没有链接、按钮语义或键盘操作入口。

### 东方快车：推理审判

- 能进入开场并显示逐段文本。
- 顶部工具条包含返回、阶段、信心值、证据、关联、时间线、帮助、笔记、重置等操作。
- 开场正文初始存在打字/加载的短暂空白；在内容出现前，中央卡片大面积留白，缺少明确加载或“点击跳过”提示。

### 血字的研究、逆转裁判：最初的逆转

- 两者均复用同一入口与游戏壳，数据格式已经被统一到共同结构。
- 本次线上快速切换时，曾出现页面保持“推理游戏”默认标题、开场为空的加载中状态。即使这是缓存或脚本时序导致的短暂状态，也说明动态脚本加载没有显式 loading/error UI，玩家只会看到空页面，无法判断需要等待、刷新还是返回。
- 逆转裁判采用 `courtroom-only` 流程，但其目标数据仍配置为 `investigation` 阶段的“收集证据/进入审判”，与纯法庭流程不一致，玩家无法在实际流程中看到这些目标。

## 问题清单

### P0：阻断或严重损害首体验

| ID | 问题 | 证据 | 影响 | 优化建议 |
|---|---|---|---|---|
| P0-01 | 原型入口标题白字白底，几乎不可读。 | `src/pages/game-design/prototype/index.astro` 的 H1 为 `text-white`；线上截图可复现。 | 用户第一眼无法识别页面用途，降低品质感和可访问性。 | 改为深色正文或让入口成为完整深色沉浸页；不要让页面局部深色、整体浅色混搭。 |
| P0-02 | 动态案件数据加载没有可视化 loading/error 状态。 | `GameState.loadCaseData()` 动态插入 script，失败依赖 `alert()`；线上切换时出现默认标题、空开场卡片。 | 弱网、缓存或脚本失败时，玩家面对空白区域，不知道下一步。 | 游戏壳先显示“正在准备案件”骨架屏；数据加载成功后再显示开场；错误改为页内错误面板，提供“重试”“返回案件列表”。 |
| P0-03 | 原型入口卡片不是语义化可交互元素。 | 卡片是带 `onclick` 的 `div`，可访问性树中仅为 container。 | 键盘、屏幕阅读器用户无法启动案件；也没有原生焦点或按压反馈。 | 用 `<a href>` 承载跳转，或使用 `<button>`；提供可见 `focus-visible` 样式、明确“开始案件”文案和 44px 以上触控区域。 |
| P0-04 | 新手教程中的高亮目标与实际 DOM 不匹配。 | `guideUI.js` 指向 `#scene-tabs`、`#witness-list`、`#notebook-btn`、`#trial-btn`；审查中未发现对应元素 ID。 | 教程承诺“指给玩家看”，实际不能定位关键操作，首次学习成本更高。 | 先定义稳定的组件 ID/`data-tour` 标识，再由教程逐项高亮和滚动定位；每个案件按流程提供自己的教程步骤。 |

### P1：核心流程和信息架构

| ID | 问题 | 证据 | 影响 | 优化建议 |
|---|---|---|---|---|
| P1-01 | 顶部同时保留主站导航和游戏工具条，游戏沉浸感被切断。 | `BaseLayout` 固定站点导航；`play.astro` 再渲染完整操作栏。 | 玩家注意力被“浏览网站”和“处理案件”两套导航分散，小屏尤其拥挤。 | 游戏页使用轻量游戏专用壳：左侧退出案件，中央案件/阶段，右侧暂停或更多菜单；将主站导航隐藏到退出路径。 |
| P1-02 | 顶部工具条把低频工具与当前主任务并列。 | 证据、关联、时间线、帮助、笔记、重置同时常驻。 | 当前目标不突出，玩家要先理解八个控件才能开始。 | 默认只保留“案件目标、证据、笔记、更多”；关联和时间线在获得相关线索后解锁或放入更多菜单；重置移入暂停菜单。 |
| P1-03 | 游戏初始行为与操作对象缺少空间引导。 | 场景对象用绝对定位热点，名称依赖 hover tooltip；调查说明仅为一段文字。 | 触摸设备没有 hover；玩家不知道哪些位置可点，也可能把探索变成扫雷。 | 首次进入场景时用一次性脉冲或标签显示可调查数量；热点提供始终可见的细小名称/图标；支持“显示可调查物”开关。 |
| P1-04 | 逆转裁判的目标与 `courtroom-only` 流程冲突。 | `data-phoenix-wright.js` 中多项目标 phase 为 `investigation`，而开场后直接进入 `trial`。 | 目标系统对该案件失效，且向玩家提示不存在的调查动作。 | 为每个 flowType 定义目标 schema；纯法庭案件应按“阅读案情 → 质询证人 → 出示证据 → 总结陈词”配置目标。构建校验必须检测目标 phase 与 flowType 的兼容性。 |
| P1-05 | 调查与审判的推进门槛主要由计数驱动。 | `minEvidence`、`minWitnesses` 作为进入审判条件。 | 玩家可以完成数量要求但不理解证据关系，推理被收集任务替代。 | 以“至少发现一个关键关系/矛盾”作为主门槛，数量要求只作辅助；在未满足时指出缺少的推理动作，而不是仅显示计数。 |
| P1-06 | 关联板和时间线属于高价值功能，但入口的命名过于抽象。 | 顶部仅显示“关联”“时间线”，依赖 emoji 辅助。 | 新玩家不知道功能边界，也无法预期点击结果。 | 改为“线索关联”“案件时间线”；首次解锁时弹出一行简短说明，且在空状态给出下一步操作。 |

### P1：无障碍、键盘与触摸

| ID | 问题 | 证据 | 影响 | 优化建议 |
|---|---|---|---|---|
| P1-07 | 多个图标按钮没有可访问名称。 | 帮助、关闭、时间线等按钮主要依赖 emoji 或 `title`；关闭按钮是“×”。 | 屏幕阅读器信息不足，鼠标悬停提示也不适用于触摸。 | 所有仅图标按钮添加 `aria-label`；保留可见 tooltip，但不要以 tooltip 替代可访问名称。 |
| P1-08 | 多数按钮只定义 `hover`，缺少统一的 `focus-visible`。 | 原型相关代码大量 `hover:*`，未见通用焦点环。 | 键盘用户不知道当前焦点；也不满足基本可访问性预期。 | 在游戏壳建立全局 `.game-button:focus-visible`，使用高对比 2-3px ring；逐项测试 Tab 顺序。 |
| P1-09 | 小型工具按钮和关闭按钮低于推荐触控尺寸。 | 顶部大量 `text-xs + px-3 py-1`，关联板关闭按钮为 `w-8 h-8`。 | 手机上容易误触，尤其在固定顶部栏内。 | 所有主操作最小 44×44px；桌面可紧凑显示，但移动端改为图标+标签的底部工具栏或“更多”抽屉。 |
| P1-10 | 对话、证据、教程、时间线弹层未见焦点圈定和 Escape 关闭。 | 弹层通过动态 HTML 和 backdrop click 实现，未处理 focus trap、初始焦点与 Esc。 | 键盘焦点可能跑到背景内容；关闭路径不完整。 | 建立统一 Dialog：打开后焦点进入标题或第一操作，Tab 限定在弹层，Esc 关闭，关闭后焦点回到触发按钮。 |
| P1-11 | 状态更新主要是视觉 Toast，未提供 `aria-live`。 | `GameUI.showToast()` 创建普通 div。 | 证据收集、目标完成、错误等更新对辅助技术不可见。 | Toast 容器加 `role="status" aria-live="polite"`；阻断性错误用 `role="alert"` 并提供重试。 |

### P2：视觉、内容与工程质量

| ID | 问题 | 证据 | 影响 | 优化建议 |
|---|---|---|---|---|
| P2-01 | 站点入口是浅色内容页，游戏是近黑界面，切换缺少过渡与共同视觉语言。 | 入口使用主站 `BaseLayout`；游戏另起深色壳。 | 视觉身份断裂，降低“进入案件”的仪式感。 | 入口可保留主站结构，但案件卡区域改为统一的“档案室”深色带；进入游戏使用 150-250ms 的淡入过渡。 |
| P2-02 | emoji 被用作系统图标、案件封面、提示和状态。 | 火车、放大镜、天平、证据、关联、时间线、帮助、笔记等均使用 emoji。 | 不同系统渲染不一致，视觉密度偏杂，难形成稳定品牌资产。 | 保留 emoji 仅作内容性装饰；系统操作改用统一线性 SVG 图标（如 Lucide），案件封面使用具备主题的插画、纹理或图标。 |
| P2-03 | 热点与场景画面较抽象，案件之间缺少可辨识的美术差异。 | 场景由渐变、简单几何与火柴人构成。 | 不足以支撑东方快车、维多利亚伦敦、法庭三种题材的情绪差异。 | 每案定义一张低成本背景插画或静态拼贴：车厢、空屋、法庭；互动热点覆盖其上。优先保证信息可读，不需要复杂动画。 |
| P2-04 | 页面固定高、固定底部证据栏与主站 footer 可能造成滚动冗余。 | 游戏容器 `min-h-screen`，内容 `pb-32`，BaseLayout 仍附带大型 footer。 | 游戏结束前出现站点页脚会破坏氛围；小屏可能有固定元素遮挡。 | 游戏页使用无 footer 的专用布局；根据证据栏实际高度给内容加安全底部内边距，采用 `dvh` 而非仅 `vh`。 |
| P2-05 | `innerHTML` 插入大量案件与玩家数据。 | 入口、场景、证据板、笔记和弹层均拼接 HTML 字符串。 | 当前本地数据风险较低，但一旦开放投稿、评论或云同步，XSS 面积很大；维护也困难。 | 对外部/玩家输入一律使用 `textContent` 或统一 escaping；长期将关键 UI 移为 Astro 组件或受控渲染函数。 |
| P2-06 | 数据加载错误仍使用原生 `alert()`。 | `gameState.js` 的案件不存在、ID 不匹配和脚本失败分支。 | 原生弹窗打断沉浸，移动端体验粗糙，也没有恢复路径。 | 用游戏内错误面板或 modal 替换，并记录可诊断信息；“重试”应重新加载指定数据文件。 |

## 三个案件的差异化建议

### 东方快车：推理审判

- 强化“列车被困”的空间感：将场景导航表现为车厢序列，不要只是通用出口按钮。
- 关键目标应围绕“谁在什么时间在哪里”展开，优先让玩家在时间线或关联板中建立一次核心关系，再进入审判。
- 12 名乘客是题材优势，但首轮建议只突出 3-4 名关键人物，避免名单和卡片过载。

### 血字的研究

- 重点是现场观察与演绎链。将 `RACHE`、戒指、脚印、烟灰分成“观察事实”和“可推导结论”，不要一次性展示 `keyInfo`。
- 在案发现场给出明确的观察顺序或可选调查清单，避免玩家漏掉绝对定位热点。
- 法庭/审判室的题材合理性较弱，可改称“推理复盘”或“警局汇报”，更贴合福尔摩斯故事语境。

### 逆转裁判：最初的逆转

- 纯法庭流程应将第一屏直接做成“案件摘要 + 已持有证物 + 开庭”而非沿用调查系统。
- 目标、教程、证据板和时间线都要切换为法庭语境：证词、追问、出示、异议、矛盾链。
- “异议”应成为一条清晰可读的动作链：选证人 → 读证词 → 标出句子 → 选择证物 → 确认，而非在整个证词下仅给一个按钮。

## 推荐交互架构

```text
案件选择
  └─ 案件卡（链接，显示开始/继续）
       └─ 游戏加载态（案件名 + 骨架屏 + 返回）
            └─ 游戏专用壳
                 ├─ 顶栏：退出 | 案件与当前任务 | 证据 | 更多
                 ├─ 主舞台：场景/法庭/对话
                 ├─ 上下文工具：只在需要时展示时间线、关联、笔记
                 └─ 暂停菜单：帮助、设置、重置、返回案件列表
```

### 工具显示规则

| 场景 | 始终显示 | 条件显示 | 收入更多菜单 |
|---|---|---|---|
| 开场 | 退出、跳过、当前章节 | 无 | 帮助、重置 |
| 调查 | 当前目标、证据 | 笔记、线索关联、时间线 | 帮助、重置 |
| 审判 | 当前证词、证据、进度 | 笔记、时间线 | 帮助、重置 |
| 结局 | 重玩、返回案件列表 | 案件复盘、成就 | 设置 |

## 分阶段实施计划

### 第一阶段：可用性修复（P0，1-2 天）

1. 修复入口标题和正文对比度，替换案例 `div onclick` 为链接或按钮。
2. 为动态案件加载增加 loading/error/retry 三态，移除 `alert()`。
3. 修复教程锚点，补齐 `data-tour` 标识并按案件流程配置教程。
4. 为纯法庭案件重写目标数据和教程；将该规则加入案件校验脚本。
5. 增加最小冒烟测试：三条案件 URL 可加载、标题正确、开场文本非空、首个主操作可点击。

**验收标准**：三案在冷启动与硬刷新下均能在 2 秒内显示 loading 或内容；失败状态不空白、不弹原生 alert；键盘可启动任一案件。

### 第二阶段：推理主循环收敛（P1，3-5 天）

1. 重新设计游戏专用顶栏，合并低频工具到更多菜单。
2. 调查场景增加可调查物提示和首次引导，确保移动端不用 hover 也能发现热点。
3. 用“关键关联/矛盾”取代单纯证据数量作为主要推进条件。
4. 将东方快车、血字和逆转裁判分别配置为封闭空间、现场推理、法庭对抗三种明确主循环。
5. 为弹层加入焦点管理、Escape、返回焦点和 `aria-live` 状态播报。

**验收标准**：第一次进入的用户无需阅读长说明，也能在 30 秒内完成第一项有效调查；每个案件的教程、目标和流程一致。

### 第三阶段：沉浸感与品质（P2，1-2 周）

1. 统一入口和游戏的主题语言，建立深色游戏 token 与案件主题色。
2. 替换系统 emoji 为统一 SVG 图标，设计三案的主题封面和场景背景。
3. 将游戏页从通用站点 footer 中剥离，完善移动端和横屏布局。
4. 收敛 `innerHTML` 动态渲染边界，先处理玩家笔记和未来投稿数据。
5. 建立 375/768/1024/1440 宽度的截图回归和关键键盘流程测试。

## 建议的验收指标

| 指标 | 当前风险 | 阶段目标 |
|---|---|---|
| 案件成功启动率 | 动态脚本失败时无恢复 UI | 99% 以上，有明确重试路径 |
| 首次有效操作时间 | 工具过多、热点不清晰 | 30 秒内完成首次调查/质询 |
| 无障碍基础 | 无焦点、部分无标签 | 所有核心操作可 Tab 操作，有名称和焦点状态 |
| 移动端可用性 | 顶栏拥挤、小按钮、hover 依赖 | 375px 无横向滚动，主按钮不小于 44px |
| 流程契约正确率 | 教程/目标/flowType 有错配 | 三案 100% 对齐并进入 build 校验 |
| 推理动作占比 | 数量收集仍较强 | 每案至少有一次玩家主动关联或证词反证后才可进入关键阶段 |

## 审查边界
