# 案件「关联作品」关系链功能方案

> 版本：v1.1  
> 日期：2026-09-13  
> 状态：待确认（已根据反馈更新）

## 一、需求背景

当前案例库按「来源类型」（推理小说 / 真实案件 / 影视 / 游戏）分类管理，共 300 个案例，但缺少跨类型的关联关系。用户在查看一个真实案件时，无法快速知道该案件是否被改编成了小说、电视剧或电影；反之，查看一部影视作品时，也不知道它的原型案件或原著小说是什么。

本方案在案例详情页增加「关联作品」板块，建立案件与作品之间的双向关系链，支持站内跳转和站外链接。

## 二、现状分析

### 2.1 项目架构

| 层级 | 位置 | 说明 |
|------|------|------|
| 数据存储 | `cases/来源类型/地区/案件名称.json` | 静态 JSON 文件，按目录分类 |
| 数据加载 | `src/lib/caseLoader.ts` | `import.meta.glob` 静态导入，构建时加载 |
| 类型定义 | `src/lib/types.ts` | TypeScript 接口 |
| 数据校验 | `schema/case.schema.json` | JSON Schema |
| 详情页 | `src/pages/case/[...slug].astro` | 故事 / 设计 / 游戏 三视图 tab，500+ 行 |
| URL 格式 | `/fun_detective/case/来源类型/地区/案件名称` | slug = `来源类型/地区/案件名称` |

### 2.2 详情页板块结构（故事视图）

当前故事视图从上到下依次为：
1. 故事摘要
2. 完整故事
3. 人物关系
4. 角色档案
5. 关键时间线
6. 结局/真相
7. **延伸阅读**（参考链接 + 推荐视频，故事视图最后一个板块）

「关联作品」将放在**延伸阅读下方**，作为故事视图的收尾板块。

### 2.3 已有相关字段

- `基本信息.来源作品/事件`：字符串，仅记录来源名称，无结构化关联
- `基本信息.参考链接`：数组，外部链接（维基 / 豆瓣 / IMDb 等）
- `基本信息.推荐视频`：数组，B站 / YouTube 视频推荐

以上字段均为单向信息展示，不支持跨案件跳转。

## 三、数据模型设计

### 3.1 新增字段

在 `基本信息` 下新增 `关联作品` 数组字段，与「参考链接」「推荐视频」同级。

```json
"关联作品": [
  {
    "作品名称": "告白",
    "作品类型": "电影",
    "关联关系": "改编为",
    "创作者": "中岛哲也（导演）",
    "年份": 2010,
    "简介": "根据凑佳苗同名小说改编，讲述女教师为女儿复仇的故事",
    "站内Slug": "影视/日本/告白",
    "外部链接": "https://movie.douban.com/subject/4268598/"
  }
]
```

### 3.2 字段定义

| 字段 | 类型 | 必填 | 说明 |
|------|------|------|------|
| `作品名称` | string | 是 | 作品名称 |
| `作品类型` | enum | 是 | `小说` / `电影` / `电视剧` / `纪录片` / `游戏` / `动画` / `漫画` / `其他` |
| `关联关系` | enum | 是 | `改编为` / `改编自` / `原型为` / `衍生` / `灵感来源` / `同系列` / `翻拍` / `其他` |
| `创作者` | string | 否 | 导演 / 作者 / 编剧等 |
| `年份` | number | 否 | 发表 / 上映年份 |
| `简介` | string | 否 | 一句话说明 |
| `站内Slug` | string | 否 | 若该作品已在案例库中，填写 `来源类型/地区/案件名称`，用于站内跳转 |
| `外部链接` | string | 否 | 豆瓣 / IMDb / 维基等外部链接，站内不存在时使用 |

### 3.3 关联关系说明（共 8 种）

| 关联关系 | 使用场景 | 示例 |
|----------|----------|------|
| `改编为` | 当前案件被改编为某作品 | 真实案件 → 「改编为」电影 |
| `改编自` | 当前作品改编自某案件 / 原著 | 影视 → 「改编自」真实案件 / 小说 |
| `原型为` | 当前作品的原型是某案件 | 影视 → 「原型为」真实案件 |
| `衍生` | 基于当前案件衍生的作品 | 真实案件 → 「衍生」纪录片 |
| `灵感来源` | 作品受当前案件启发 | 小说 → 「灵感来源」真实案件 |
| `同系列` | 同一系列的其他作品 | 推理小说 → 「同系列」系列其他作品 |
| `翻拍` | 翻拍 / 被翻拍 | 中国《误杀》→ 「翻拍」印度《误杀瞒天记》 |
| `其他` | 以上未覆盖的关系 | — |

### 3.4 双向关联策略

采用**单向存储 + 运行时反向索引**策略：

- **正向**：每个案件的 `关联作品` 数组中存储它指向的作品
- **反向**：在 `caseLoader.ts` 中构建反向索引，扫描所有案件的 `关联作品`，通过 `站内Slug` 匹配，自动生成「被哪些案件关联」的列表
- **反向关系自动转换**：

| 对方填写的关系 | 本方显示的关系 |
|----------------|----------------|
| 改编为 | 改编自 |
| 改编自 | 改编为 |
| 原型为 | 改编为 |
| 衍生 | 灵感来源 |
| 灵感来源 | 衍生 |
| 同系列 | 同系列 |
| 翻拍 | 翻拍 |

**优势**：
- 数据只存一份，不会出现双向数据不同步
- 构建时计算，静态站点无性能问题
- 新增关联时只需修改一端

## 四、UI 展示设计

### 4.1 板块位置

放在故事视图中**延伸阅读板块下方**，作为故事视图的最后一个板块。

```
故事视图:
  ├── 故事摘要
  ├── 完整故事
  ├── 人物关系
  ├── 角色档案
  ├── 关键时间线
  ├── 结局/真相
  ├── 延伸阅读（参考链接 + 推荐视频）
  └── 🔗 关联作品  ← 新增
```

### 4.2 组件抽取决策

**抽取为独立组件 `src/components/RelatedWorks.astro`**，理由：
1. 详情页已 500+ 行，继续内联会降低可读性
2. 关联作品卡片包含较多条件逻辑（正向/反向合并、类型图标映射、关系标签、站内/站外跳转判断）
3. 未来可能在首页「相关推荐」或分类页复用
4. 与现有 `CaseCard.astro` 组件的设计模式一致（可复用卡片抽取为组件）

### 4.3 卡片样式

每个关联作品展示为一张横向卡片，整体风格与「延伸阅读」的链接卡片保持一致但信息更丰富：

```
┌──────────────────────────────────────────────────┐
│ 🎬 电影            2010          [改编为]         │
│ 告白                                              │
│ 中岛哲也（导演）                                   │
│ 根据凑佳苗同名小说改编，讲述女教师为女儿复仇的故事    │
│                                    [查看详情 →]   │
└──────────────────────────────────────────────────┘
```

- 顶部行：作品类型图标 + 作品类型 + 年份 + 关联关系标签
- 作品名称（加粗，主标题）
- 创作者（次要信息）
- 简介（次要信息，最多 2 行）
- 右下角：跳转按钮
  - 站内作品：`查看详情 →`，点击跳转 `/fun_detective/case/{slug}`
  - 站外作品：`了解更多 ↗`，新标签页打开外部链接

### 4.4 作品类型图标映射

| 作品类型 | 图标 |
|----------|------|
| 小说 | 📖 |
| 电影 | 🎬 |
| 电视剧 | 📺 |
| 纪录片 | 🎥 |
| 游戏 | 🎮 |
| 动画 | 🎨 |
| 漫画 | 📚 |
| 其他 | 🔗 |

### 4.5 布局

- 桌面端：2 列网格（与延伸阅读的单列链接区分，信息密度更高）
- 移动端：单列堆叠
- 无关联作品（正向 + 反向均为空）时：整个板块不渲染

## 六、实施步骤

### 步骤 1：更新类型定义

文件：`src/lib/types.ts`

- 新增 `RelatedWork` 接口（含 8 种关联关系联合类型）
- 在 `BasicInfo` 中增加 `关联作品?: RelatedWork[]`

### 步骤 2：更新 JSON Schema

文件：`schema/case.schema.json`

- 在 `基本信息.properties` 中增加 `关联作品` 数组定义
- `作品类型` 枚举：小说 / 电影 / 电视剧 / 纪录片 / 游戏 / 动画 / 漫画 / 其他
- `关联关系` 枚举：改编为 / 改编自 / 原型为 / 衍生 / 灵感来源 / 同系列 / 翻拍 / 其他

### 步骤 3：扩展数据加载器

文件：`src/lib/caseLoader.ts`

- 新增 `buildReverseRelationIndex()` 函数：扫描所有案件的 `关联作品`，通过 `站内Slug` 构建反向索引
- 新增 `getRelatedWorks(slug)` 函数：返回正向 + 反向合并后的关联作品列表，反向关系按 3.4 表自动转换
- 反向关联的条目标注 `_isReverse: true`，用于 UI 区分（可选）

### 步骤 4：创建关联作品组件

文件：`src/components/RelatedWorks.astro`（新增）

- Props：`works: RelatedWork[]`（已合并正向+反向）
- 内部逻辑：类型图标映射、站内/站外跳转判断、卡片渲染
- 空数组时不渲染任何内容

### 步骤 5：更新详情页

文件：`src/pages/case/[...slug].astro`

- 导入 `getRelatedWorks` 和 `RelatedWorks` 组件
- 在 frontmatter 中调用 `getRelatedWorks(caseData.slug)` 获取合并后的关联作品
- 在故事视图中，延伸阅读板块下方增加：
  ```astro
  {hasRelatedWorks && (
    <div class="card p-6 mt-8">
      <h2 class="text-xl font-bold mb-4 text-primary-800">🔗 关联作品</h2>
      <RelatedWorks works={relatedWorks} />
    </div>
  )}
  ```

### 步骤 6：批量填充数据

编写脚本 `scripts/add-related-works.cjs`，根据第五章的清单批量为 JSON 文件写入 `关联作品` 字段。

- 第一批：站内互链数据（约 60-80 个文件）
- 第二批：站外链接数据（约 7 个文件）
- 同系列数据：为系列中每个作品填写同系列其他作品的 `站内Slug`

### 步骤 7：构建验证

- 运行 `npm run build` 确认构建通过
- 抽查 3-5 个详情页，验证关联作品板块渲染
- 验证站内跳转（告白 ↔ 告白小说、误杀 ↔ 误杀瞒天记）
- 验证反向关联自动生成（如在小说端只填「改编为电影」，电影端自动显示「改编自小说」）
- 验证站外链接新标签页打开

1. **首页筛选**：在首页增加「有改编作品的真实案件」筛选维度
