> 文档版本：v1.0
> 创建日期：2026-08-28
> 设计路径：Architectural（brainstorming skill 全流程）
> 状态：待用户评审

---

## 1. 项目概述

### 1.1 核心目标

构建一个网罗全球虚拟与真实案件的结构化案例库，同时服务于两大用途：
- **小说/短文阅读**：作为推理故事的阅读素材库
- **游戏设计支持**：作为推理游戏、剧本杀、互动叙事的设计参考库

### 1.2 终局用户与演进路径

采用**混合路径**，从个人工具起步，逐步扩展：

| 阶段 | 用户范围 | 核心形态 |
|---|---|---|
| 阶段1 | 个人（创建者） | 飞书 Base 内部工具 |
| 阶段2 | 个人 + 小范围分享 | 公开内容网站 |
| 阶段3 | 创作者小群体 | 网站 + 创作辅助工具 |
| 阶段4 | 公开社区 | 平台 + API + 社区协作 |

### 1.3 终局产品形态

按优先级逐步叠加的组合形态：
1. **内容型网站/知识库**（阶段2）— 推理案件的结构化浏览、搜索、筛选
2. **创作辅助工具**（阶段3）— 诡计组合、线索链设计、逻辑检查、大纲生成
3. **社区/平台**（阶段4）— 用户贡献、协作创作、评分评论
4. **API/数据服务**（阶段4）— 标准化 API 供第三方应用调用

### 2.2 核心设计原则

1. **飞书 Base 是唯一录入入口**——所有内容在 Base 里编辑，Git 是只读数据镜像
2. **Git 是唯一数据资产**——网站、工具、API 都从 Git 读数据，不直接连飞书
3. **同步是单向的**——Base → Git，永远不从 Git 反写回 Base
4. **JSON 是标准交换格式**——所有下游系统消费同一份 JSON 数据
5. **数据可移植优先**——任何阶段都可以脱离飞书独立运行

### 3.3 命名规范

| 对象 | 规则 | 示例 |
|---|---|---|
| 目录名 | 中文，与飞书枚举值完全一致 | `虚构推理/日本/` |
| 文件名 | 案件名称.json，去除特殊字符 | `嫌疑人X的献身.json` |
| 案件ID | `case-` + 3位数字，按录入顺序 | `case-001` |
| 字段名 | 与飞书 Base 字段名一致（中文） | `案件名称` |

### 3.4 数据校验规则

同步脚本在写入 Git 前必须校验：

1. **必填字段**：案件名称、来源类型、地区、一句话简介、录入状态
2. **枚举值合法**：来源类型、地区、案件状态、诡计类型等必须在预定义列表内
3. **难度评分范围**：1-5 分，综合分 = 三项平均分（四舍五入到1位小数）
4. **文件路径正确**：目录结构必须与案件的来源类型、地区一致
5. **JSON 格式合法**：可被标准 JSON 解析器解析
6. **游戏字段条件必填**：来源类型为"游戏案例"时，游戏平台、玩法类型为必填

校验不通过的记录跳过并记录到错误日志，不写入 Git。

## 4. 同步机制设计

### 4.1 触发方式：混合模式（定时 + 手动）

- **自动同步**：GitHub Actions 每天凌晨定时运行一次
- **手动同步**：随时运行 `python scripts/sync_from_lark.py` 触发即时同步
- **未来升级**：案例量上来后，可升级为飞书自动化 + Webhook 即时触发

### 4.2 同步脚本核心逻辑

```
1. 从飞书 API 读取案件库主表 + 线索链子表的全部记录
2. 按记录 ID 与 Git 仓库现有文件对比：
   - 新增记录 → 创建新 JSON 文件
   - 变更记录 → 更新现有 JSON 文件
   - 删除记录 → 移入 /archive/ 目录（不直接删除）
3. 对每条记录做数据校验（必填字段、枚举值、难度分范围）
4. 校验通过的记录写入对应目录（来源类型/地区/案件名称.json）
5. 生成全量导出（all_cases.json + all_cases.csv）
6. 生成同步报告（新增X条、更新Y条、删除Z条、错误W条）
7. Git add → commit → push 到 GitHub
```

### 4.3 增量同步策略

- **首次同步**：全量读取，写入所有文件
- **后续同步**：按飞书记录的「最后更新」时间字段，只同步上次同步后变更的记录
- **兜底机制**：每周做一次全量同步，防止增量遗漏

### 4.4 Git 提交策略

| 场景 | 提交信息格式 | 分支 |
|---|---|---|
| 日常自动同步 | `sync: 自动同步 YYYY-MM-DD HH:mm（新增X，更新Y）` | main |
| 手动同步 | `sync: 手动同步 - 原因说明` | main |
| 数据结构变更 | `feat: 新增XX字段 / 调整目录结构` | feature/xxx → PR |
| 脚本更新 | `chore: 同步脚本优化` | feature/xxx → PR |

### 4.5 错误处理

- **飞书 API 失败**：重试3次（间隔10秒），仍失败则记录错误并跳过本次同步
- **数据校验失败**：跳过该条记录，记录到 `errors/YYYY-MM-DD.log`，同步报告中标注
- **Git 冲突**：同步前 `git pull --rebase`，冲突时暂停并报警（单向同步理论上无冲突）
- **部分成功**：只要有至少一条记录成功同步就提交；全部失败则不提交

### 4.6 同步报告

每次同步后生成 `reports/YYYY-MM-DD-HHmm.md`，包含：概览统计、新增列表、更新列表、校验失败列表。

## 5. 前端展示层设计（阶段2）

### 5.1 技术选型：Astro

- 内容站默认零 JS，加载速度极快
- 需要交互的组件（搜索、筛选器）局部用 React
- 未来升级创作工具时，可平滑过渡到 SSR 模式
- 与 Git 仓库 JSON 数据天然契合

### 5.2 网站结构

```
首页 /
├── 推荐案件（编辑精选 + 随机推荐）
├── 分类导航（按来源类型 / 按诡计类型 / 按难度）
└── 统计数据（案件总数、覆盖地区、诡计类型分布）

案件库 /cases
├── 筛选器（来源类型、地区、年代、诡计类型、难度区间、案件状态）

├── 基本信息栏
├── 故事阅读模式（默认折叠剧透，点击展开）

设计参考 /design
├── 诡计类型索引
```

### 5.3 核心功能

| 功能 | 优先级 | 实现方式 |
|---|---|---|
| 多维度筛选 | P0 | 前端基于 JSON 数据本地筛选 |
| 全文搜索 | P0 | Pagefind（静态站搜索，零后端） |
| 剧透保护 | P0 | 结局/真相默认折叠，点击展开 |
| 双模式切换 | P0 | 故事阅读 / 设计参考 Tab 切换 |
| 关联推荐 | P1 | 基于标签相似度的简单算法 |
| 随机案件 | P1 | 前端随机抽取，激发灵感 |
| 难度可视化 | P1 | 雷达图展示三项难度分 |
| 线索链时间线 | P2 | 可视化组件展示线索出现顺序 |
| 暗黑模式 | P2 | CSS 变量切换 |

### 5.4 设计风格

- **整体调性**：推理小说质感——深色背景、衬线字体标题、神秘感
- **主色调**：深墨绿 + 米白 + 暗红点缀
- **排版**：案件详情页用书籍式排版，宽行距、大段文字舒适阅读
- **交互**：悬停有微妙动效，展开/折叠有过渡动画
- **响应式**：移动端优先，桌面端优化阅读体验

### 5.5 部署方式：Vercel

- 与 GitHub 仓库一键集成，每次 push 自动部署
- 全球 CDN，免费额度充足
- 预览分支功能方便调试
- 国内访问慢的问题，后续可加 Cloudflare CDN

### 5.6 阶段2进入条件与交付物

**进入条件**：
- 阶段1完成：50个深度案例录入完毕
- 同步脚本稳定运行至少2周
- JSON 数据格式经过实际验证，无大的结构调整

**交付物**：
- 可访问的网站域名
- 首页 + 案件列表 + 案件详情 + 悬案专区 四个核心页面
- 筛选 + 搜索 + 剧透保护 三个核心功能
- 移动端适配

## 7. 创作工具层设计（阶段3）

### 7.1 工具一：诡计组合器

**输入**：诡计类型、可复用机制、难度目标、场景设定、目标受众
**输出**：匹配的参考案例（3-5个）、案件设计草稿、难度预估、潜在漏洞提醒
**技术**：案件库标签匹配 + AI 大模型生成

### 7.2 工具二：线索链设计器

**功能**：可视化拖拽设计线索链，系统检查合理性和信息差
**画布操作**：添加线索节点、连接关系、设置指向结论、调整出现顺序
**系统反馈**：信息差分析、逻辑闭环检查、难度评估、参考案例推荐
**技术**：React Flow 可视化画布 + 后端逻辑校验

### 7.3 工具三：逻辑检查器

**检查维度**：诡计可行性、线索充分性、信息差合理性、人物动机、时间线一致性、红鲱鱼有效性
**输出**：漏洞清单（严重/警告/建议）、参考案例、修改建议
**技术**：AI 大模型分析 + 规则引擎（常见逻辑漏洞模式匹配）

### 7.4 工具四：故事大纲生成器

**输入**：案件设计、体裁、叙事视角、目标长度
**输出**：三幕/五幕结构大纲、关键场景列表、人物弧光建议、节奏控制、参考案例

### 7.5 技术架构

阶段3采用**纯前端 + 第三方 AI API**的轻量方案，不需要自建后端：
- 前端：Astro + React 岛屿
- AI 调用：直接调用大模型 API（豆包等）
- 案件库数据：从 Git 仓库静态加载
- 用户生成内容：本地存储（阶段4再加后端）

## 8. 社区/API 层设计（阶段4）

### 8.1 REST API

```
GET  /api/cases              # 案件列表（筛选、分页、排序）
GET  /api/cases/:id          # 案件详情
GET  /api/cases/random       # 随机案件
GET  /api/cases/similar      # 相似案件推荐
GET  /api/tags               # 所有标签
GET  /api/stats              # 统计数据
GET  /api/design-patterns    # 游戏设计模板
POST /api/tools/*            # 创作工具 API
```

认证：API Key（开发者申请）；限流：免费100次/天，付费按需；格式：JSON。

### 8.2 社区功能

| 功能 | 优先级 |
|---|---|
| 用户注册/登录（邮箱/OAuth） | P0 |
| 案件贡献（提交→审核→入库） | P0 |
| 案件纠错（提交修改建议） | P0 |
| 评论/讨论 | P1 |
| 评分/难度投票 | P1 |
| 收藏/书单 | P1 |
| 改编/Fork | P2 |
| 创作分享 | P2 |

### 8.3 贡献审核流程

```
用户提交案件 → 自动校验（格式、必填、查重）
    → 社区投票（3名以上老用户通过）
    → 管理员终审 → 入库 → 自动同步到 Git 仓库
```

Git 仓库仍然是唯一数据资产，社区贡献审核通过后由自动化脚本提交到 Git。

## 附录：设计决策记录

| 决策点 | 选择 | 理由 |
|---|---|---|
| 演进路径 | 混合路径（个人→团队→社区→公开） | 风险最低，逐步验证 |
| 终局形态 | 组合形态（网站→工具→社区→API） | 逐步叠加价值，不做一次性大而全 |
| 架构方案 | 双轨并行（Base CMS + Git 数据仓库） | 兼顾录入易用性和数据可移植性 |
| Git 托管 | GitHub | 用户已有仓库，生态成熟 |
| 同步触发 | 定时+手动混合 | 成本低，可控，未来可升级 |
| 文件粒度 | 每案件一个JSON，按来源类型+地区分目录 | 便于浏览和版本管理 |
| 线索存储 | 阶段1内嵌在案件JSON | 简单自包含，未来再独立 |
| 前端框架 | Astro | 性能好，可渐进升级 |
| 部署 | Vercel | 与 GitHub 集成好，自动部署 |
| 创作工具架构 | 纯前端+AI API | 阶段3轻量起步，不需要自建后端 |
